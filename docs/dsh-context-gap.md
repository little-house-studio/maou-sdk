# DSH 上下文管理对照报告 —— 只谈「上下文」这一件事

对照本机已装的 **dsh 0.1.1-rc.2**（`/Applications/DSH Desktop.app` 内 `@deepseek-ai/*` 约 150 个包）与当前 **maou-sdk**（`core/context`、`core/agent`、`core/llm`、`core/tools`、`cli`、`app`）。

范围收窄：只看上下文管理——窗口与计量、压缩、大输出处理、动态注入、历史与回放。权限、UI、插件、子代理编排等已在 `dsh-gap.md` 里写过的不重复。

读法同 `dsh-gap.md`：每条先讲「你会碰到什么」，再讲他们怎么让你省心，再讲我们现在会怎样，最后给建议。引号里的英文是模型真能看到的通知原文（文案本身是设计的一部分）。

---

## 总体结论

两边思路同源（分层压缩 + 头尾保留 + 结构化摘要 prompt 高度相似，maou 的 8 节摘要格式与 DSH 逐节一致），但 DSH 把上下文做成了**一条闭环的证据链**：所有测量走同一把尺子，所有改写都是"投影"而非删除，所有给模型的提示有固定原文、失败有固定人话。我们的零件大多都有，还多了几件他们没有的（微压缩、语义压缩、超窗退避），缺的是把这些零件**拧成一套互相咬合、出了事说人话**的体系。

差距按用户痛感排序，前三名：

1. **大输出没有"外溢"**：被截断的内容永久丢失，模型只能重跑命令。
2. **窗口大小兜底 65536**：用大窗口模型时压缩会来得太早，白花冤枉钱。
3. **占用条在第一轮回复前恒为 0**：尺子只认上一条 API 回报，开工前是盲的。

---

## 一、多少算"满了"：窗口大小和尺子

### 1. 换了个百万窗口的模型，压缩还是按 6.5 万算

**你会碰到什么**：你在设置里选了个 1M 窗口的模型，想着"这次可以聊久一点了"。结果聊到 6 万多 token 它就开始压摘要——因为配置里没填 `maxContext`，代码兜底按 65536 算。每压一次就多一笔摘要调用费，而这个窗口明明还有 90% 空着。

**他们怎么做**：窗口大小永远由模型适配器给出（`dsh-llm.resolveModelInfo(...).context.contextWindow`，DeepSeek 目录默认 1,000,000），压缩、计量、UI 全部从这一个数派生。用户填错或不填，至少默认值属于"这个模型真实的大小"。

**我们现在会怎样**：`preset.maxContext ?? preset.maxTokens ?? 65536`（`core/agent/src/agent/runtime.ts:2625`、`core/context/src/compressor.ts:141`）。`maxContext` 来自 2026-06-21 的 models.dev 快照目录，模型不在目录里就落到 65536。

**建议**：把"窗口兜底值"从硬编码 65536 改成随模型目录走 + 明显偏大的保守值（如 200K），并在 `/context` 里把"当前窗口来源"写出来（目录 / 预设 / 兜底），让用户看得出这个数是猜的。

### 2. 占用条在第一轮回复前恒为 0

**你会碰到什么**：新开会话，你一上来就贴了 10 张图、贴了一个两万行的报错日志，然后盯着输入框旁边那个占用环——显示 0%。它没坏，它只是"只认上一条 API 回报的用量"（`core/context/src/token-estimate.ts:1-4`：「只认上一条 API usage 的 input + output。不估算正文」）。第一句还没发出去，尺子上没有数。

**他们怎么做**：一个会话级 `tokenMeter` 单例，平时用固定启发式（4 字符/token + 每块 4 开销）累计，厂商回报用量且请求头逐字节没变时才把锚点换成官方数。所以**任何时刻**都有读数——第一条消息发出前也有。

**我们现在会怎样**：决策和展示其实有两把尺：压缩决策认 usage，UI 分区面板（`ContextMeter` + `composeContextBreakdown`）是启发式估算再缩放到 usage 上。首条消息前 usage 为 0，环就是 0；中间每轮之间读数也不动。

**建议**：保留"usage 锚点优先"（这是对的，比纯估算准），但给锚点缺失的窗口补启发式读数，两条腿合成一个数。我们已有正文估算器（CJK 1 字 ≈ 1 token，`core/types/src/token-estimate.ts`），把它接到"没有锚点时"即可。

### 3. 计量和压缩是不是同一把尺子

**你会碰到什么**：占用条显示 78%，你等它压；结果它没压，下一轮直接 85% 才压。或者反过来，条上的分区（系统/工具/消息）加起来和总数对不上。

**他们怎么做**：压缩只读 `tokenMeter.measure()`；meter 对"压缩替换"有一套阴影计价协议（替换区间必须与计价事件对齐，否则直接抛错），UI 的占用投影在压缩落地**瞬间**变短，且 UI 投影明确声明不参与任何决策——决策只有一个入口。DSH 的分区面板也老实写明三块加总与官方总数对不齐的差额归 overhead。

**我们现在会怎样**：其实已经接近——`clearLastOccupancy` 让压缩后占用清零、条立刻变短，`/context` 也标了三段 heuristic。差的是"锚点缺失时的读数"（上一条）和锚点恢复时机。

**建议**：优先补第 2 条；"同一把尺"的架构我们已基本成立，保持别让第三处 estimator 长出来。

## 二、快满的时候：自动压缩

### 4. 压缩切点会不会把一次工具调用切成两半

**你会碰到什么**：压缩把旧消息摘要掉。如果切点正好落在"模型发起调用"和"工具返回结果"中间，剩下的历史里就会有一个没有结果的孤儿调用——有的厂商直接报 400，有的模型开始对着空气脑补结果。

**他们怎么做**：压缩范围选择时从尾部累加到保留线，再**回退到"工具对平衡"的切点**（`toolPairingBalancedBefore`），任何会拆散 call/result 对的边界直接报错拒绝（错误文案就写明 "would split a step's tool-call/result pair"）。压缩是结构性保证，不是事后修补。

**我们现在会怎样**：保尾部 16% 原文区 + 近 2 组工具对，发请求前还有 `repairOrphanedToolCalls` 兜底补一句"[系统自动补充] 工具 X 的执行结果因服务中断或异常未能返回"（`core/context/src/message-builder.ts:308`）。也就是说：我们靠"保留窗口够大 + 事后修补"，他们靠"切点根本不会落在对中间"。我们的兜底文案是防御性的（"没返回"），会让模型以为是故障；实际是压缩切掉的，语义不同。

**建议**：在压缩范围选择处加同样的平衡边界检查（我们已有配对分类器 `tool-recovery.ts`，可直接复用），把 `repairOrphanedToolCalls` 降级为真正的故障兜底，而不是压缩的日常路径。

### 5. 摘要前先"白捡"一轮：能不花钱就先不花钱

**你会碰到什么**：上下文超阈值，系统直接开始调 LLM 写摘要——哪怕其实只需要把几个几万字的旧工具输出剪掉就够，摘要这一笔钱本可以不花。

**他们怎么做**：压力达标后**先**跑无 LLM 的工具结果剪枝（8192 字符以上剪成头 4096 + 标记 + 尾 1024），重新计量，低于阈值就**跳过摘要**（`dsh-compaction-basic` :883-887）。摘要只留给剪枝救不回来的局面。

**我们现在会怎样**：这步我们其实领先——我们有**三级**体系（70% 微压缩无 LLM 头尾剪 → 80% LLM 摘要 → 90% 归档），微压缩就是"不花钱先剪"。但顺序上我们是"阈值到哪级做哪级"，他们是"先做便宜的、重测、不够再做贵的"。

**建议**：把我们的微压缩也接成"剪完重测、达标即止"的复检流程（大概率已接近，确认 `window-pressure.ts` 与 staged 模块的判定顺序即可），这是一条"用户账单"层面的差距，值得在 CHANGELOG 里讲。

### 6. 摘要写得比原文还长怎么办

**你会碰到什么**：极端情况下摘要模型跑飞，写出的"摘要"比被压缩的原文还大——上下文没省反而更满，还收了钱。

**他们怎么做**：摘要落库前校验：`estimateMessage(checkpoint) >= 被遮蔽区 token 数` 就拒绝整个压缩，表层保持原样（`dsh-compaction-basic` :556）。

**我们现在会怎样**：未发现对应的"摘要必须更小"校验；我们有摘要上限 `MICRO_SUMMARY_MAX_CHARS = 100`（只管微压缩）和大压缩的 task 分组，但没有"整体必须净变小"的终检。

**建议**：加一条终检，成本一行，堵住一类"越压越满"的病理。

### 7. 压缩失败时，你说得出是哪一步坏了吗

**你会碰到什么**：你手动 `/compact`，它转了一会儿回你一句"失败"。是正忙？是摘要模型抽风？是写盘失败？不知道。 meanwhile 新打的字卡不卡也不知道。

**他们怎么做**：手动压缩只在空闲时可用（忙时明确回 "Compaction is unavailable because this process has an active compaction, or the agent is not idle."）；失败路径按阶段给固定文案（`No compactable history yet.` / `changed` / `summary` / `commit` / `persistence` 各自不同）；压缩全程持锁，锁没放干净下一个人能看到"compressing"并拒绝并发。压缩失败**表层绝不变**——你不会得到半份摘要。

**我们现在会怎样**：`/compact` 走 `forceCompressSession`，成功有漂亮文案（"✅ 上下文已压缩 · 大压缩 · token X → Y"）；失败路径是 catch 后"本轮不压，15s 后重试"的日志（`[ContextEngine] 压缩失败，本轮跳过并在 15s 后重试`），没有用户可读的分阶段错误。compact lock 有检测（`compactLockOpen`），好。

**建议**：把失败原因收成一张人话表（正忙 / 内容变了 / 摘要失败 / 提交失败 / 没写成磁盘），斜杠命令直接显示对应那条。这是纯文案工程，一天能做完，用户感知提升最大。

### 8. 压缩本身也在花你的钱：热前缀复用

**你会碰到什么**：每次自动压缩，摘要调用都要把"整段旧对话"再读一遍——按 input 计费。对话越长，压一次越贵，而这段内容上一轮明明刚刚发过。

**他们怎么做**：摘要调用把会话前缀**逐字重放**（相同的 system + tools + 被压缩区原文），摘要指令只作为最后一条 user 消息追加，让厂商的 KV cache 认出"这段刚发过"，命中缓存价。加上平时请求头逐字节比较、只在变化时才换 header（`request/header` reason: initial/resume/change），把缓存命中的机会最大化。

**我们现在会怎样**：有"文件缓存区/稳定前缀"设计和技能稳定排序（防缓存破坏的意识在），但摘要调用没有把"前缀重放"当硬要求（`dsh-gap.md` #10 自认）。

**建议**：摘要 prompt 追加式重构（前缀原样 + 指令在最后一条 user 消息）值得照抄——实现不难，对账单是直接折扣。

## 三、一句命令吐出几万字：大输出的去留

### 9. 被截断的部分，永久消失了

**你会碰到什么**：`grep -r` 吐了三万行。我们截成头尾几百行给模型，中间标一句 `... [Omitted N chars.] ...`。下一轮模型说"我想看刚才被省略的中间那段"——**拿不回来了**，只能重跑一遍命令。命令有副作用（或很慢）时，这就是用户在等第二次。

**他们怎么做**：三道闸，最关键的是第二道——
1. **当场截**（output-retention）：按字节预算留头/尾，UTF-8 切口都对齐，附中性省略说明 `Omitted N bytes.` + 工具自己的恢复指引（如 "Results capped at 100. Narrow the pattern, path, or include to see more."）；
2. **外溢 spill**：超过 `maxInlineBytes` 的**纯文本**结果全文写进会话旁的私有文件（0600 权限），模型看到的替换文本是"头尾预览 + 一句通知"：
   > `(Omitted 48213 bytes. Full formatted result stored at: /…/session-…/…-bash.txt. Use read with offset/limit, or grep this path to search within it.)`
   
   于是"看全文"从**重跑**变成**读文件**，一次读、按 offset 翻、能 grep。外溢失败时保留原文内联，绝不把成功说成失败；`read` 工具的结果明确排除在外溢之外，防"读→溢→再读"死循环。
3. **压前再剪**（compaction 时 tool-result-pruner，见第 5 条）。

**我们现在会怎样**：有第 1 道和第 3 道（`output-compressor.ts`、`prune-text.ts`），没有第 2 道。`dsh-gap.md` #12 已自认。

**建议**：这是我们上下文管理**唯一必须补的硬缺口**。照 DSH 的形状抄：会话目录旁 `spill/` 子目录 + 预览 + 固定通知文案 + "read 工具豁免" + "外溢失败不改判结果"。我们的 `result_limit`（终端默认 5000 字符）截掉的原文现在是真的没了。

### 10. 截断的时候，说人话和给出路

**你会碰到什么**：模型看到 `... [Omitted N chars.] ...`，不知道该怎么继续——是换个命令？是缩小范围？还是这段其实无关紧要？

**他们怎么做**：省略说明是"中性事实 + 工具自己的出路"两段拼接：`Omitted N items. Results capped at 50. Narrow the pattern, path, or include to see more.`。且 `truncated` 语义被严格定义：只表示"预算内省略了本可获得的内容"，绝不暗示上游出错。

**我们现在会怎样**：文案已统一走 `omission.ts`（"精确数量或 unknown，不编数字"——这点和他们对齐了），但"给模型的下一步出路"（narrow the pattern 这类）没做成每个工具的标配。

**建议**：给每个会产生截断的工具补一句"出路"文案。便宜，且直接影响模型行为质量。

### 11. 读文件这把尺：分页 vs 一次切

**你会碰到什么**：读一个 5000 行的文件。我们按 `max_chars` 一刀切；模型要往后看，得自己猜行号再调一次。

**他们怎么做**：read 是独立渲染器：单行超 2000 字符截断、整窗 50KiB 上限，页脚带下一步——`(Showing lines 1-800 of 5000. Use offset=801 to continue.)` 或 `(End of file - total 5000 lines)`。模型拿到的是"接着读"的准确指令，不用猜。

**我们现在会怎样**：我们有个他们没有的亮点——`mode: signatures`（只回函数/类签名），大文件首次侦察比他们聪明。差的是**分页页脚**这种"把下一步写给模型"的仪式。

**建议**：read 工具加自动页脚。一行模板的事。

## 四、一直在变的东西：动态上下文

### 12. 状态注入：同一张快照被反复当新闻播

**你会碰到什么**：动态状态（时间、项目状态、环境信息）每轮都注入一遍。模型的历史里堆了十几条几乎一样的"当前状态"，窗口被重复文本占掉，模型还会困惑哪条才是最新的。

**他们怎么做**：动态上下文是**带来源的快照消息**，头部一行：`Current runtime context. This snapshot supersedes earlier runtime-context snapshots.`（新快照覆盖旧快照）；**文本没变就不注入**；上下文变空时注入显式清除：`Current runtime context: none. Earlier runtime-context snapshots no longer apply.`。所以模型永远能分清"哪条有效"。

**我们现在会怎样**：子轮动态注入改走 system 消息（避免模型当新用户发言，这个动机是对的），但没有"变了才注入"的去重，也没有显式清除。

**建议**：抄三件套：supersedes 头 + 变化才注入 + 变空显式清。对窗口和模型心智都是净收益。

### 13. 项目说明书改了，正在聊的这场不知道

**你会碰到什么**：聊到一半你改了 `AGENTS.md`（比如加了条新规矩），正在跑的对话完全不知情，模型还按旧规矩干活到这场结束。

**他们怎么做**：跟随第一方 read/write/edit 成功事件，对每个指令文件比对内容摘要；变了就注入 `Updated instructions from: AGENTS.md`，删了就注入 `Instructions removed: ...` + `The previously loaded instructions from this file no longer apply.`；压缩把旧基线遮蔽后，下一步自动重组并声明 `This complete workspace instruction baseline replaces all earlier workspace instruction baselines.`。还有预算：超预算先丢宽泛文件、再二分截断最具体的文件，且**去重**（CLAUDE.md 和 AGENTS.md 内容一样只注入一次）。

**我们现在会怎样**：启动时编译进系统提示，中途无变更检测（`dsh-gap.md` #62 自认，本次复核仍成立）。同名去重未发现。

**建议**：分两步走：先做"压缩遮蔽后基线重组"（我们的摘要会遮蔽系统提示尾部注入的技能/规则，这条现在就缺）；再做变更检测（我们已有文件监听基础设施可挂）。

### 14. 模型不知道现在几点

**你会碰到什么**：你说"今天下午部署"，模型只能猜今天几号；跨时区协作时"下午"更是猜错。

**他们怎么做**：可选的时间上下文注入，原文：
> `Time sampled while preparing turn 3, step 1: 2026-08-29T14:03:27GMT+08:00[Asia/Shanghai]`
> `Browser time zone for this request: Asia/Shanghai. Interpret otherwise-unqualified dates and times in this zone.`
> `Elapsed since the preceding step: 4m 12s.`

带刷新间隔（不是每句刷钟），时区混乱时明确让模型问你。

**我们现在会怎样**：没有默认注入；模板留了钩子（before_user 可放 `{{>>script/get-time.py}}`），等于把这件事丢给每个模板作者。

**建议**：把它下沉为核心能力（间隔刷新 + 快照去重），模板钩子保留作为覆盖口。

### 15. 模型对着同一个命令连撞三次

**你会碰到什么**：测试挂了，模型用一模一样的命令重跑了五遍，每遍都是同样的报错。烧 token、烧时间，直到轮数上限。

**他们怎么做**：`repeat-tool-reminder`：同名工具 + 完全相同参数连击到 3 次给一句提醒（`You are repeating the exact same tool call with identical arguments. ... try a different approach`），5 次、8 次升级成点名警告（tool 名、次数、完整参数、`Do not call this tool with these exact arguments again.`）。用户发新消息自动清零计数；被拒绝的调用也计数。

**我们现在会怎样**：未发现对应机制。我们有子代理预算熔断（softRequestBudget），但主循环内没有"原地打转"检测。

**建议**：照抄，默认 [3,5,8]。实现是一个 WeakMap + post-execute 钩子，防呆收益巨大。

### 16. 技能目录：旧名单作废要说清楚

**你会碰到什么**：技能装了卸、卸了装，模型历史里留着几代技能名单。它可能去调用一个已经删掉的技能名。

**他们怎么做**：技能目录带 digest，变化时发**整目录替换**消息并声明：`The available skill catalog changed. This complete catalog replaces every earlier available-skills list in this session:`；清空时：`No skills are currently available... Do not use names from earlier skill catalogs.`。目录描述超 500 字符截断，控制目录本身的体积。

**我们现在会怎样**：有 `<available_skills>` 首轮索引 + `<skill_update>` 增量更新，机制同源。差"旧名单作废"的显式声明和"只许模型调 / 仅用户可点"的分级（dsh-gap #63，仍成立）。

**建议**：给 `<skill_update>` 补"替换语义"一句话文案；注册表分级放到技能体系专项里做。

## 五、压完之后：历史去哪了

### 17. 压缩不该是删除：事件的账本要能倒带

**你会碰到什么**：一场长对话被压缩了三轮。后来你想知道"最早那条报错原文是什么"——如果压缩是物理删除，就没有"最早那条"了。

**他们怎么做**：会话是**仅追加的事件日志**，模型看到的 messages 是日志的**派生投影**；压缩、剪枝、指令更新全部是位置性的 `replace` 投影操作，原日志一字不动。配套：任何切分点可 fork 出子会话（回到过去）、压缩检查点带 `compactionId` 可跨进程识别、重建一致性断言（从日志重放出的请求必须和当年发出的逐字节相等，否则启动即失败——烂账藏不住）。

**我们现在会怎样**：基础其实齐了——`events.jsonl` 只追加、harness 工作集是派生文件且有 `.bak`、`prefix_ref` 分支树支持 fork。差的是"回看被压缩前的原文"在 UI 上没有入口（用户和模型都看不到"压缩遮蔽了什么"），以及"从日志重建请求"的一致性自检。

**建议**：不必照搬整套事件溯源。两个低成本动作：① 摘要消息带上"被压缩区间的 seq 范围"，UI 里点摘要能展开原文区间；② 加一个开发模式断言：重启恢复后重放一轮 buildMessages，与上次请求 messages 做哈希比对，不对齐报警。这条是信任基建。

### 18. 关键时刻必须已经在盘上

**你会碰到什么**：模型正要回答、正要跑命令的一瞬间死机。再打开，最近几句没了。

**他们怎么做**：三个屏障强制 flush：发请求给模型**前**、工具体执行**前**、下一请求组装**前**，flush 失败直接阻断（fail-closed）；平时 200ms 合并窗口批量写。也就是说"任何不可逆动作之前，账必先落盘"。

**我们现在会怎样**：`dsh-gap.md` #5 的自评（"开口问模型之前没有同一条硬规矩"）本次未发现反证，仍成立。我们有冷恢复兜账（见下条），所以丢的是"那一小段"，不是整场。

**建议**：在发请求前加 flush 屏障。低频写盘场景可以只在"非 last-write 超过 N 秒"时强刷，避免为每个 token 落盘。

### 19. 恢复时的诚实度：不知道就说不知道

**你会碰到什么**：崩在上一个工具执行到一半。恢复后模型看到什么，决定它会不会盲目重跑一条有副作用的命令（比如再删一次分支）。

**他们怎么做**：给中断的工具补两种结果之一，文案把不确定性写明：
> `The tool call was interrupted after it was recorded, but no result was durably recorded. Its outcome is unknown. Decide whether to retry from the tool semantics: retry only if the operation is read-only or idempotent; ...`
> `The tool call was interrupted before the Harness recorded it as started. Retry it if it is still needed.`

**我们现在会怎样**：这里**我们其实已经做平甚至更好**——`recoverColdTools` 区分"已派发结局未知"（`只重试只读或幂等的事，不要盲目重跑有副作用的操作`）和"还没开始可以再试"两种文案，语义与他们对齐；`recoverColdTurn` 还会补轮次结尾。**`dsh-gap.md` #7 说"半截轮次没有补结束规矩"已过时**，代码里实现了（`session-store.ts:1272-1283`）。

**建议**：无需跟进，更新旧文档即可。这条写进报告是为了防止"照清单重复建设"。

## 六、我们已经不差、不用羡慕的部分

对照要公平。这些是我们有、他们没有或不如我们的：

- **微压缩**（无 LLM 头尾剪）和**三级阈值**（70/80/90）：他们只有"剪枝 + 摘要"两级，我们的分界更细，成本低的一级更大。
- **超窗三级退避**（0.50→0.35→0.22 预算 + `emergencyTrimMessages` 兜底文案）：他们溢出恢复只重试 1 次；我们多撑两轮，且兜底文案诚实（"完整记录仍在会话存储中；可 /compact 或新开话题"）。
- **测试输出的语义压缩**（`compressTestOutput`：只留失败行 + 摘要）：比纯字节头尾预算聪明，是他们 output-retention 没有的。
- **图片整批验收 + 内容寻址**（4 张 / 8MB / 8192px，超限整批拒绝，sha256 入库，报错人话）：`dsh-gap.md` #54 说我们没做——**已过时**，`core/context/src/attachment-store.ts` 已完整实现。
- **压缩重试退避**（15s）与 compact lock 检测：崩溃在压缩中途不会压坏数据。
- **子代理 kind 体系**（fork/helper/task/project 四种，helper 强制无工具只读）：比他们的 fork/spawn 两态细。
- **MCP gateway 元工具**（模型只见一个 `mcp` 工具 + 提示注入）：和他们的 code-runtime 思路同源，工具多时省窗口。
- **断连 fail-closed**：MCP 单连接失败不阻断其他连接，死亡连接的工具从注册表卸下——方向与 #64 一致，颗粒度可再核。
